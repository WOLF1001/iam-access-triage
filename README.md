# iam-triage — AI-assisted triage потоку запитів на доступи

Прототип для тестового завдання HOLYWATER TECH · IAM Engineer.

## Проблема

Увесь потік звернень про доступи, ліцензії, ключі, ліміти й діагностику входу тримає **одна людина**. Аналіз 108 реальних (знеособлених) звернень ([`docs/process/current-state.md`](docs/process/current-state.md)) показує, куди йде її час:

- **26%** звернень приходять без критичних даних (яка система, для кого, список людей) → спершу коло уточнень;
- **24%** — не за адресою: не IAM, або відповідь уже існує;
- **26%** — про AI-тули (ліміти Claude, API-ключі, MCP-конектори): новий потік без процедур;
- рішення й апруви живуть у DM: немає сліду, немає SoD, **bus factor = 1**;
- **жодна система не є source of truth** «хто-що-має-мати»: Okta не бачить non-SSO SaaS, HRIS — без SCIM і з затримкою, 1Password знає про vault-и, але не про те, де секрет використовується.

## Рішення

**LLM розбирає текст, policy вирішує.** LLM перетворює «брудне» звернення на структуру: тип, згадані системи, сигнали, чого бракує. Маршрут обирає детермінована policy (`config/policy.yaml`) за сигналами з трьох незалежних джерел:
- regex по тексту;
- LLM;
- факти з систем (HRIS, Okta, журнал апрувів).

Правила можуть лише **підняти** маршрут. Будь-яка невизначеність веде до людини.

```
Slack → n8n → redact → LLM-парсер → валідація схеми → заземлення на текст → злиття сигналів → policy → зона
```

### Три зони

| Зона | Що робить бот | Вхід у зону (коротко) | Із 108 |
|---|---|---|---|
| **AUTO** | діє сам: birthright-група, повторний інвайт за чинним апрувом, read-only діагностика | дія з allowlist **і** всі передумови підтверджені **системою**, а не текстом; автор = суб'єкт; одна система; жодного ризик-сигналу | 1 |
| **DEFLECT** | відповідає статтею з KB або переадресовує в чергу | відповідь існує в KB (Published) або це не IAM; немає ризик-сигналів | 26 |
| *шлюз NEED_INFO* | ставить конкретні питання | бракує системи / суб'єкта / списку / скоупу — не апрув «наосліп» | 21 |
| **HUMAN з апрувом** | готує план, виконує після кнопки апрувера | звичайна видача, ліміти, ліцензії, ключі | 15 |
| **HUMAN-ONLY** | лише пакет контексту; не діє навіть після апруву | привілеї, prod, фінансові системи, PII, SoD, офбординг, **від імені іншої людини**, секрети, атака на акаунт | 45 |

Межі виведено з реєстру ризиків: Critical/High → HUMAN-ONLY, Medium → апрув, Low і дія зворотна → AUTO. Для критичних систем межа свідомо проведена **ширше**: зайва ескалація коштує хвилини людини, пропущена — інцидент, який не відкотити. Деталі й контролі ISO 27001 / SOC 2 — [`docs/zones.md`](docs/zones.md), обґрунтування — [ADR-0003](docs/adr/0003-zone-boundaries.md).

## Як перевірено

- **497 тестів за ~6 с:**
  - інваріанти безпеки;
  - property-based «LLM як противник» (hypothesis);
  - metamorphic «додали ризикову фразу — маршрут не знизився»;
  - секрети не виходять за межу redaction;
  - golden snapshot усіх 108 маршрутів.
- **Golden set граничних звернень** ([`tests/golden/cases.yaml`](tests/golden/cases.yaml)): 30 «брудних» кейсів, 15 — на межах зон. Серед них «терміново додай мене в адмінку», запит від імені колеги, prompt injection у тексті й у треді, невідома система, два типи в одному, homoglyph. Одне відоме обмеження лишено як чесний `xfail`.
- **Тести знайшли діри в моєму ж коді, написаному з AI:**
  - критична: LLM «розбивала» запит на адмінку в 1Password на безневинні підзапити й отримувала AUTO;
  - через API можна було діяти від імені будь-якого співробітника;
  - n8n зберігав секрети до redaction.

  Усе закрито. Журнал — [`ai-artifacts/ai-mistakes.md`](ai-artifacts/ai-mistakes.md) (22 записи).
- **Живий стек:** n8n (Slack-подія → маршрут → дія) і Notion (база знань, синк, чернетки для `kb_gap`) працюють наживо, а не на моках.

## Запуск

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest -q                         # 497 тестів
.venv/bin/python run_demo.py --all                    # демо 16 кейсів + розподіл по 108 (без ключа LLM)
.venv/bin/python tools/stand.py                       # веб-стенд http://localhost:8765 (dev-режим)
```

У їхньому стеку (n8n + Slack-подія + Notion): `cp .env.example .env` (токени `KB_SYNC_TOKEN`, `TRIAGE_API_TOKEN`), далі `colima start && docker compose up -d --build`; n8n — `:5678`. Воркфлоу — `tools/build_n8n_workflow.py`, Notion — [`notion/README.md`](notion/README.md).

## Свідомі обмеження

Повно й чесно — [`docs/critique.md`](docs/critique.md). Головне:
1. **З людини повністю знімається лише ~25%** звернень, а після розширення HUMAN-ONLY людині дістається 60 зі 108. Цінність — повне звернення з фактами, а не «автоматизація всього». Час людини не виміряно: потрібен baseline.
2. **З реальною LLM прогнано лише локальну `qwen3:14b`** ([`demo/full_run_ollama.md`](demo/full_run_ollama.md)). Безпека трималась (0 маршрутів, нижчих за rules, — після виправлення, яке цей прогін і знайшов), а цінність упала: без людини закривається 3 зі 108 замість 27. Потрібні тюнінг промпта під локальну модель або Claude Haiku; точність не відкалібрована на розмітці людиною.
3. **Read-side — моки з ідеальними даними.** У реальності HRIS запізнюється, джерела суперечать одне одному, у фактів немає `observed_at`.
4. **n8n — найпривілейованіший компонент:** бачить сирий текст до redaction, тримає креди.
5. **Немає:** воркфлоу апруву (кнопка → виконання), стану треду після NEED_INFO, спільного сховища для дедупу.

## Що далі

1. **Baseline** (2 тижні): час до відповіді, частка кіл уточнень, розмітка 200 звернень людиною.
2. **Shadow-режим** (2–4 тижні): бот пише лише внутрішню нотатку; головна метрика — **override rate**.
3. Вмикати по черзі: DEFLECT і NEED_INFO → AUTO по одній дії з kill switch.
4. Воркфлоу апруву, деградований режим при недоступності LLM, ingress-redaction до n8n.
