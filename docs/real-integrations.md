## 1. Device Inventory Reconciler — звірка без source of truth

**Що це.** Внутрішній сервіс (FastAPI + React, Kubernetes на AWS EKS), який я спроєктував і побудував.
- Звіряє обладнання між **Jamf Pro, Microsoft Intune, Active Directory, Jira Assets і Google Workspace**.
- Кожна розбіжність автоматично отримує severity.
- Доступ — через SAML, API — через session-based token, аудит дій — в OpenSearch.

### Кейс: «одна машина — дві назви»

Як це виглядало в інтерфейсі (дані замінено):

| Джерело | Запис A | Запис B |
|---|---|---|
| **Jira Assets** | `WIN-100231`, serial `SN-MOCK-0042`, статус **In Stock**, не бачили ~730 днів | `WIN-100874`, serial **порожній**, статус **In Use**, у полі `old asset tag` — `100231` |
| **Active Directory** | немає | є: `WIN-100874`, Windows 11, вхід 21 год тому, акаунт активний |
| **Microsoft Intune** | немає | **немає** |
| **Jamf Pro** | N/A (Windows) | N/A (Windows) |
| **Google Workspace** | знайдено **за серійником `SN-MOCK-0042`**: поточна назва `WIN-100874`, остання синхронізація 2 год тому, корпоративний пристрій | — |

**Що зробила система:**

1. **Склеїла два записи за серійником, а не за назвою.** Назву хоста змінюють при переінсталяції чи перейменуванні, серійник — ні. Лише Google Workspace знав обидва атрибути разом: серійник і поточну назву. Тому для цієї зв'язки джерелом правди стало саме GWS. Інтерфейс так і пише: *Google Workspace is the source of truth for this machine*.
2. **Розрізнила «очікувано» і «проблема».**
   - Для запису A («In Stock») відсутність в AD і Intune позначена як очікувана: машина на складі не має бути в домені.
   - Для запису B («In Use») відсутність в Intune — проблема: машина в роботі, з корпоративним акаунтом, але без керування.
   Severity залежить від статусу, а не лише від факту відсутності.
3. **Підняла дві знахідки рівня CRITICAL:**
   - зайвий запис у Jira (одна машина під двома назвами, назва в Jira ≠ назва в MDM);
   - машина в роботі, але не в Intune.
4. **Не виправила нічого сама.** Через «Create Jira task» на відповідальну за актив людину (поле *responsible* у Jira Assets) створено задачу. Задача містить контекст з усіх джерел: які системи що бачать, за яким ключем склеєно, чому це CRITICAL. Виправлення робить власник даних, а не сервіс звірки. «Sync device» — ручне оновлення фактів по одній машині, щоб перевірити результат після виправлення.

**Результат:** знайшли справжній хост, а відповідальна людина за задачею виправила облік (зайвий запис у Jira). Окремо всплила некерована машина в роботі. Жодне джерело окремо цього не показувало: Jira мав обидва записи, AD бачив лише одну назву, Intune — жодної.

### Що з цього перенесено в triage-прототип

| Урок із Reconciler | Як це в triage |
|---|---|
| Ключ для зв'язки має бути стабільним (серійник, а не hostname) | ідентичність автора — `event.user` зі Slack → email → HRIS / Okta, а не ім'я з тексту звернення |
| Source of truth — для конкретного атрибута, а не для системи загалом | HRIS — правда про «людина активна / менеджер», Okta — про SSO-призначення, журнал апрувів — про «погоджено» |
| Розбіжність — це знахідка, а не помилка | `source_conflict` → людина (#92: звернення «останній день», HRIS — active) |
| Severity залежить від контексту | «всі доступи» — це broad scope для запиту на видачу, але очікуваний скоуп для offboarding |
| Ключ знахідки — фізична сутність, а не запис (інакше дубль задач) | бракує в прототипі: немає дедупу звернень (#5/#36/#62) і за `event_id` — `critique.md` §1.3, §3.7 |
| Поріг застарілості (90 днів) | бракує в прототипі: у фактів read-side немає `observed_at` → `critique.md` §1.1 |
| Система підсвічує, виправляє власник даних — задачею з повним контекстом | AUTO лише для трьох дій з allowlist; решта — ескалація (JSM + внутрішня нотатка з фактами read-side і dry-run планом) або апрув власнику ресурсу з каталогу |

### Граблі

- **Власники систем, чиї дані підсвічує звірка, кажуть «у нас усе ок».** Реліз оголошував письмово, з конкретними прикладами розбіжностей, а не загальними словами.
- **Baseline-метрики треба знімати до запуску.** Інакше неможливо показати, що стало краще.
- **Знахідка прив'язана до запису, а не до фізичної машини.** Задача створюється з того запису, на якому її натиснули, і там же відображається її статус. Але «одна машина — дві назви» — це одна проблема про два записи, які система пов'язує за однаковими даними (серійником). Тому на записі A стоїть «тікет у роботі», а на записі B — «no ticket». Ризик: людина, що відкрила запис B, створить дубль задачі на ту саму проблему. Правильний ключ знахідки — фізична сутність (серійник або пара записів), а не окремий запис.

## 2. Граблі, набиті в цьому прототипі

Інтеграції n8n і Notion тут живі, не моки. По дорозі:

| Що сталося | Як виявив | Що зробив |
|---|---|---|
| n8n зберігав дані виконань → тестовий секрет із #32 осів у БД n8n **до** redaction у сервісі | канарейковий тест: `grep` по SQLite у контейнері | вимкнув збереження виконань (воркфлоу + env). Залишок у WAL — у `critique.md` §3.2 |
| `docker compose restart` не перечитує `.env` → n8n не бачив `NOTION_KB_DATABASE_ID` | Config-вузол упав із зрозумілою помилкою (так і задумано) | `docker compose up -d` (пересоздання контейнера) |
| Після `n8n import` + `publish` перший запит пішов у **стару** версію воркфлоу | неочікувана 500 на валідний тест | після публікації — рестарт і очікування, поки інстанс підхопить версію |
| Експорт воркфлоу з n8n містить email власника | перевірка експорту перед комітом | у репо лише згенерований JSON (`tools/build_n8n_*.py`), без експорту з UI |
| Тип властивості Notion після імпорту CSV невідомий (text / select / status) | — (передбачив заздалегідь) | воркфлоу спершу читає схему бази й будує властивості під фактичні типи |
| Порожній синк від Notion (інтеграцію не підключено до бази) тихо вимкнув би всі DOCS | тест | сервіс відхиляє порожній або обрізаний (<50%) синк з 409, KB лишається попередньою |
| «Merge with CSV» у Notion **додає** рядки, а не оновлює → усі 21 стаття ×2 → синк відхилено (`дубль article_id`), бот лишився на попередній KB. Причину було видно лише в n8n, а сервіс спершу називав лише перший дубль | 409 у лозі сервісу | сервіс пише причину в лог і перелічує **всі** дублі одразу; базу імпортовано начисто |
| Нова база після реімпорту — нова сторінка: інтеграція до неї не підключена → Notion 404 `object_not_found`, і синк узагалі не доходив до сервісу (три прогони поспіль — тиша) | лог n8n: «shared with your integration "ys"» | підключити інтеграцію до бази (Connections). Висновок: на «тишу» синку потрібен алерт, а не лише на 409 |
| Базу «IAM KB» опубліковано в інтернет (Publish to web): внутрішній IAM-процес доступний будь-кому з посиланням | відкрив посилання без входу в Notion | вимкнути Publish; синк ходить через інтеграцію, публічне посилання йому не потрібне |
| `data/requests.csv` з правами `600` → у контейнері від non-root сервіс не читав датасет | 500 на стенді в контейнері | `chmod a+rX` в образі, запис — лише в `/app/runtime` |
| Помилка запису кешу LLM перетворювала вже оплачену відповідь на rules-fallback | розбір шляхів помилок перед реальним прогоном | запис кешу не фатальний; `run_demo` падає, якщо LLM тихо деградувала |
