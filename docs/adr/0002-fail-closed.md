# ADR-0002: Fail-closed за замовчуванням

**Status:** Accepted (реалізовано; деградований режим — відкритий action item)
**Date:** 2026-10-07
**Deciders:** власник IAM-процесу (я); security

## Context

Система рішень може не знати відповіді з багатьох причин:
- LLM недоступна, перевищено ліміт, таймаут;
- LLM повернула невалідний JSON, невідомий тип або низьку впевненість;
- система не змаплена на каталог (`unknown_app`);
- джерела суперечать одне одному (Okta active, HRIS terminated);
- сервіс рішень недоступний для n8n;
- синк KB із Notion повернув порожній набір.

У кожному з цих випадків треба обрати, куди падати: в бік дії чи в бік людини.

## Decision

**Будь-яка невизначеність веде вгору по спектру маршрутів, ніколи вниз.** Автодії в такому стані заборонені.

| Збій | Поведінка |
|---|---|
| невалідний вихід LLM / невідомий тип | тип `unclear`, впевненість 0 → HUMAN_REVIEW |
| мережа / ключ / квота LLM | rules-класифікатор з впевненістю ≤ 0.5 → усе ≥ HUMAN_REVIEW, без дій |
| низька впевненість (< 0.7) | HUMAN_REVIEW |
| невідома система | NEED_INFO («яка саме тула?»), без вгадування |
| конфлікт джерел, автор не верифікований | HUMAN_REVIEW |
| сервіс рішень недоступний (n8n) | гілка помилки HTTP-вузла → HUMAN, нічого не виконується |
| невідомий маршрут від сервісу | fallback-вихід Switch → HUMAN |
| порожній / обрізаний синк KB | 409, KB лишається попередньою, DM IAM |
| тиха деградація LLM на rules у прогоні | `run_demo` завершується з помилкою, а не видає rules за LLM |

## Options Considered

### Option A: Fail-open (best effort)

Невалідний вихід → найімовірніший маршрут; недоступна LLM → лише regex, але з нормальною довірою.

| Dimension | Assessment |
|---|---|
| Доступність | Висока: людина не отримує лавину |
| Безпека | **Низька**: збій або атака на LLM (провокування невалідного виходу) може дати AUTO |
| Аудит | «Чому видали?» → «модель упала, вгадали» |

### Option B (обрано): Fail-closed → людина

| Dimension | Assessment |
|---|---|
| Доступність | **Низька при збої**: недоступність LLM = кожне звернення до людини |
| Безпека | Висока: збій ніколи не дає дії |
| Аудит | Кожна причина фіксується (`low_confidence`, `precondition_failed`, `triage_service_error`) |

### Option C: Retry, потім fail-closed

Те саме, що B, але з повторами. SDK Anthropic уже ретраїть 408/409/429/5xx (2 спроби) — тобто це частина B, а не альтернатива.

## Trade-off Analysis

У доступу асиметрична ціна помилки: зайва ескалація коштує хвилини людини, а помилкова видача — інцидент, який не відкотити (бачений секрет лишається побаченим). Тому B.

Ціна B реальна і для цієї команди особлива: **потік тримає одна людина**. Повна недоступність LLM означає, що всі 108 звернень опиняються в HUMAN_REVIEW (перевірено тестом `test_llm_outage_degrades_up_not_down`). Для однієї людини це вже не «безпечна деградація», а DoS. Тому B потребує деградованого режиму (action item 1).

## Consequences

**Стає простіше:** довіряти системі. Кожен збій видимий і веде до людини; немає класу помилок «тихо видали».

**Стає складніше:** доступність залежить від LLM-провайдера; потрібен моніторинг частки `rules-fallback` і `low_confidence`.

**Переглянути:** після shadow-періоду — реальну частку fail-closed, бо якщо вона висока, це проблема якості промпта, а не інфраструктури.

## Action Items

1. [ ] Деградований режим: при недоступності LLM DOCS і REROUTE дозволено з rules-класифікатора лише для звернень з regex-підлогою = 0; решта стає в чергу із затримкою, а не в DM.
2. [ ] Алерт на частку `rules-fallback` > N% за годину.
3. [x] Тести fail-closed: outage, битий JSON, нечислова впевненість, невідомий тип (`tests/test_invariants.py::TestFailClosedAndDeterminism`).
