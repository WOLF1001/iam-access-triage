# ADR-0003: Межі зон AUTO / DEFLECT / HUMAN-ONLY

**Status:** Accepted (межі — у [`docs/zones.md`](../zones.md); чотири розширення HUMAN-ONLY реалізуються у фазі 5)
**Date:** 2026-10-07
**Deciders:** власник IAM-процесу (я); security; DPO / юрист — для PII

## Context

- Потік звернень (`docs/process/current-state.md`) різнорідний: від «що таке Okta» до «заблокуйте всі доступи, останній день».
- Завдання прямо каже: обґрунтований флоу ескалації цінніший за «система впевнено вирішує все».
- Треба визначити, за яким принципом звернення потрапляє в кожну зону, щоб межі можна було перевірити тестом і пояснити аудитору.

## Decision

1. **Межу визначає клас ризику, а не впевненість моделі.** Реєстр ризиків (ймовірність × вплив) дає рівень, рівень дає зону:
   - Critical / High → HUMAN-ONLY;
   - Medium → HUMAN з апрувом;
   - Low і дія зворотна → AUTO;
   - немає дії → DEFLECT.
2. **Пріоритет:** HUMAN-ONLY > HUMAN (апрув) > NEED_INFO (шлюз) > DEFLECT > AUTO. Будь-який критерій вищої зони перемагає.
3. **AUTO — лише за allowlist дій і всіма передумовами з read-side** (7 умов у `zones.md` §2).
4. **Для критичних систем межа HUMAN-ONLY проводиться ширше, а не вужче.** Прийнято 2026-10-07:
   - видача доступу від імені іншої людини — HUMAN-ONLY, навіть якщо автор — менеджер суб'єкта;
   - фінансові системи;
   - prod;
   - SoD-конфлікти.

## Options Considered

### Option A: Числовий risk score із порогами

Сума ваг сигналів → якщо score > X, то HUMAN, якщо > Y — SECURITY.

| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Пояснюваність | Низька: «score = 7» нічого не каже людині чи аудитору |
| Безпека | **Ризик компенсації**: багато «м'яких» сигналів можуть переважити один критичний, або навпаки, критичний не набере порогу |
| Калібрування | Ваги довільні без даних |

### Option B: Маршрутизація за впевненістю LLM

Висока впевненість → AUTO / DEFLECT, низька → людина.

| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Безпека | **Низька**: впевненість, яку LLM повідомляє про себе, погано відкалібрована, і нею можна маніпулювати текстом звернення |
| Відповідність | Не відповідає на питання «чому цей клас не можна автоматизувати» |

### Option C (обрано): Клас ризику → мінімальний маршрут, лише вгору

Кожен сигнал має `min_route` у `policy.yaml → hard_rules`; підсумковий маршрут — максимум по всіх. Score лишається, але лише для пріоритету в черзі.

| Dimension | Assessment |
|---|---|
| Complexity | Medium: ~30 правил у YAML |
| Пояснюваність | Висока: кожне рішення = список правил, що спрацювали, з причиною (`reasons`) |
| Безпека | Немає компенсації: один критичний сигнал → HUMAN-ONLY незалежно від решти |
| Відповідність | Кожен клас HUMAN-ONLY прив'язано до контролю (ISO 27001 A.5.3, 5.15–5.18, 8.2, 8.31–8.32, 5.34; SOC 2 CC6.1–6.3, CC7, CC8.1) |

## Trade-off Analysis

C консервативніший за A: два середні ризики не стають «високим». Компенсація тут небезпечніша за консерватизм: агрегування сигналів лишаємо людині, якій бот передає їх усі.

Ціна:
- повністю з людини знімається лише ~25% звернень;
- після розширення HUMAN-ONLY (рішення 4) — ще менше: частина `on_behalf` і `financial_data` переходить з APPROVAL у HUMAN.

Це свідомий вибір: для однієї людини ескалація з повним контекстом дешевша за розбір інциденту.

## Consequences

**Стає простіше:**
- перевіряти межі тестами (golden snapshot + тест на кожен клас);
- відповідати аудитору «чому це не автоматизовано»;
- розширювати: новий клас = новий сигнал + рядок у `hard_rules`.

**Стає складніше:** частка AUTO мала (1–2 зі 108); ефект системи — DEFLECT, NEED_INFO і якість пакета для людини, а не автоматизація.

**Переглянути:**
- після shadow-періоду: які класи HUMAN-ONLY людина **завжди** погоджує без змін — кандидати на APPROVAL;
- розширення на SoD потребує надійного джерела «хто апрувер» (каталог + HRIS).
