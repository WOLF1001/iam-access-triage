# Ключові рішення (ADR-lite)

Кожне рішення: контекст → рішення → чому → ціна.

## D1. LLM — парсер, policy engine — суддя

- **Контекст:** звернення «брудні», LLM добре їх розуміє, але її вихід недетермінований і піддається prompt injection (текст звернення — недовірений ввід).
- **Рішення:** LLM повертає лише структуру через tool use зі строгою JSON-схемою. Маршрут обирає детермінований код за YAML-політикою.
- **Чому:** маршрут має бути відтворюваним, тестованим і аудитованим. Помилка LLM у найгіршому разі піднімає маршрут або дає DOCS без дії, але не призводить до видачі доступу.
- **Ціна:** policy треба підтримувати вручну; нові типи звернень потребують правок у YAML.

## D2. Три незалежні джерела сигналів: text (regex) ∪ llm ∪ read-side

- **Рішення:** regex-детектори працюють завжди; LLM може лише додати сигнали; read-side дає факти з систем.
- **Чому:** захист від «LLM забула про ризик». Regex дає false positives — це дешевше (зайва ескалація), ніж false negative (небезпечна авто-дія).
- **Ціна:** зайві ескалації на хибних збігах regex (див. `ai-artifacts/ai-mistakes.md`).

## D3. Python core замість n8n як основи

- **Контекст:** їхній стек — n8n/Make + Slack + Notion + LLM API.
- **Рішення:** логіка рішення — Python-модуль; n8n/Slack — тонка обгортка (trigger → HTTP → відповідь).
- **Чому:** policy-as-code тестується (`pytest`), рев'юється через diff, відтворюється офлайн. У n8n складні гілки рішень важко тестувати і рев'юїти.
- **Ціна:** колезі без Python складніше правити логіку; компроміс — уся політика в YAML, не в коді.

## D4. AUTO лише з allowlist + read-side preconditions

- **Рішення:** три дії: `resend_invite` (є записаний апрув), `add_birthright_group` (група в allowlist бота, requester активний у HRIS), `readonly_diagnostic`.
- **Чому:** будь-яка дія, що розширює права, має мати підтвердження з системи, а не зі слів. «Лід в курсі» ≠ апрув.
- **Ціна:** низька частка AUTO (~1–10%); основна економія — DOCS + NEED_INFO + підготовлені апруви.

## D5. NEED_INFO як gate

- **Рішення:** якщо бракує критичних даних (система, суб'єкт, список людей), маршрут = NEED_INFO з `next_route`, навіть якщо далі потрібен апрув.
- **Чому:** апрув «наосліп» = апрувер погоджує щось неконкретне → over-granting.

## D6. Діагностика без знахідок ≠ вирішено

- **Рішення:** `readonly_diagnostic` без пояснення в read-side → NEED_INFO (просимо скрін/час), а не AUTO «усе ок».
- **Чому:** знайдено як помилку AI під час розробки (#1, #3, #15 потрапляли в AUTO).

## D7. Critical-tier ресурси — тільки людина

- **Рішення:** 1Password, платіжні системи, HRIS (`risk_tier: critical`) — HUMAN_REVIEW навіть з апрувом.
- **Чому:** шеринг vault або доступ до диспутів не відкликається «чисто» — секрети, які людина бачила, лишаються скомпрометованими.

## D8. Синтетичні requester'и і треди в демо

- **Контекст:** CSV не містить автора і треду, а без них read-side перевірки неможливі.
- **Рішення:** `demo/sample.yaml` задає синтетичного автора для кожного кейсу; повний прогін — «типовий співробітник» `UGEN`.
- **Чому:** чесно показати, що рішення залежить від ідентичності автора, і не приховувати це припущення.

## D9. Відповіді користувачу — з шаблонів і KB, нейтральні

- **Рішення:** чернетки не генеруються LLM вільно; у тексті для користувача не пишемо «підозра на соц. інженерію».
- **Чому:** бот не може пообіцяти те, що policy не дозволила; атакуючий не дізнається, яке правило спрацювало.

## D10. Вихід LLM заземлюється на текст звернення (ADR-010)

- **Контекст:** adversarial-тести показали, що LLM через `summary` підзапитів і `app_mentions` могла «прибрати» regex-сигнали і обрати entitlement для AUTO (GAP-1/2, `ai-artifacts/02-architecture-review.md`).
- **Рішення:** summary/згадки приймаються лише якщо дослівно є в тексті (після Unicode-нормалізації); regex-сигнали повного тексту — підлога для підзапитів; порядок app — за текстом; AUTO лише для однієї entitlement.
- **Чому:** D1 («LLM — парсер») декларувався, але не був enforced у коді. Тепер інваріант «маршрут ≥ regex-підлога» перевіряється property-тестом без винятків.
- **Ціна:** змішані запити консервативніші; нормалізовані LLM назви («табло»→«tableau») відкидаються, якщо їх немає в тексті.
