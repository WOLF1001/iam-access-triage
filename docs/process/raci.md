## Process Document: обробка IAM-звернень з AI-triage

**Owner:** IAM-інженер (власник policy) | **Last Updated:** 2026-10-07 | **Review Cadence:** щокварталу + після кожного інциденту

> Фаза 7 (`operations:process-doc`). Зони — [`docs/zones.md`](../zones.md), поточний стан — [`current-state.md`](current-state.md).

### Purpose

Хто що робить, коли звернення проходить через бота, і як змінюється роль людини, яка сьогодні тримає весь потік сама.

### Scope

**Включено:**
- звернення про доступи, ліцензії, ключі, ліміти, діагностику входу, онбординг і офбординг у Slack-каналі IAM;
- підтримка policy, каталогу й KB.

**Виключено:**
- періодичний перегляд доступів (access review) — бот дає для нього журнал, але сам процес окремий;
- закупівля ліцензій;
- реагування на інциденти після передачі в security.

### Ролі

| Роль | Хто |
|---|---|
| **Бот** | triage-сервіс + n8n (`docs/architecture.md`) |
| **Автор** | співробітник, що пише звернення |
| **Менеджер** | лінійний менеджер автора / суб'єкта за HRIS |
| **Власник ресурсу** | `owner` у `config/app_catalog.yaml` |
| **Бюджет-власник** | погоджує витрати (ліцензії, ліміти, seat-и) |
| **IAM-інженер** | сьогоднішня «одна людина» |
| **Security** | інциденти, вразливості, політики, конектори |
| **HR** | джерело правди про прийом / звільнення (HRIS) |
| **DPO / юрист** | PII, правова підстава, LLM-провайдер |

**SoD закладено в саму матрицю:**
- там, де IAM-інженер виконує (R) критичну дію, відповідальність (A) лежить на іншій ролі: security для SoD, HR для офбордингу, DPO для PII;
- **зміни самої policy** погоджує security, а не той, хто їх пише.

### Process Flow

```
Slack → бот: redaction → розбір → сигнали → policy
   ├─ бракує даних ──────────────→ NEED_INFO: питання автору ──→ (відповідь) → знову triage
   ├─ AUTO ──────────────────────→ дія + журнал + відповідь (runbooks/)
   ├─ DEFLECT ───────────────────→ стаття KB / черга
   ├─ HUMAN з апрувом ───────────→ кнопка апруверу → бот виконує план → перевірка читанням
   ├─ HUMAN-ONLY ────────────────→ handoff (templates/human-handoff.md) → IAM-інженер вирішує й виконує
   └─ SECURITY ──────────────────→ пейдж security + handoff
                                    ↓
          IAM-інженер щотижня: overrides → зміни policy (PR + рев'ю security) → golden snapshot
```

### Detailed Steps

#### Step 1: Прийом і triage
- **Who:** бот
- **When:** нове повідомлення в каналі / DM боту
- **How:** redaction → розбір LLM (або rules) → заземлення → злиття сигналів → policy. Автор = `event.user` (підписаний Slack), а не ім'я з тексту.
- **Output:** рішення з причинами + чернетка відповіді + запис у журнал.

#### Step 2: Уточнення (NEED_INFO), якщо бракує даних
- **Who:** бот питає, автор відповідає
- **When:** немає системи, суб'єкта, списку людей чи скоупу. На HUMAN-маршруті бот теж питає одразу, щоб інженер не робив цього вдруге.
- **Output:** повне звернення.

#### Step 3: Виконання за зоною
- **AUTO:** бот за [`runbooks/`](../../runbooks/README.md).
- **HUMAN з апрувом:** апрувер натискає кнопку; бот виконує dry-run план і перевіряє результат читанням з системи.
- **HUMAN-ONLY:** IAM-інженер отримує handoff, вирішує й виконує сам.
- **SECURITY:** on-call security.

#### Step 4: Щотижневий огляд (власник policy)
- **Who:** IAM-інженер
- **When:** щотижня, 30–60 хв
- **How:**
  1. переглянути **overrides**: де людина змінила маршрут бота і чому;
  2. переглянути беклог `kb_gap` → написати статті для частих тем;
  3. переглянути **патерни** з дедупу (≥3 автори на ту саму систему й тип) → known issue або стаття;
  4. зміни policy — через PR з тестами й diff маршрутів, рев'ю security.
- **Output:** PR зі змінами policy / каталогу / KB.

### Як змінюється роль «однієї людини»

| | Сьогодні | З ботом |
|---|---|---|
| Роль | **виконавець**: читає, уточнює, шукає апрувера, видає, відповідає | **власник policy**: визначає межі, вирішує лише HUMAN-ONLY, покращує систему |
| Що робить руками | усе | HUMAN-ONLY (привілеї, prod, фінанси, SoD, PII, офбординг, від імені інших) + KB / policy |
| Звідки знає контекст | з пам'яті й переписки | handoff: факти з систем, причини, dry-run план, відповіді автора |
| Знання | у голові (bus factor = 1) | у `config/*.yaml`, KB, runbooks, тестах — колега може підхопити |
| Хто погоджує його рішення | ніхто | зміни policy — security (SoD) |
| Головна метрика | швидкість відповіді | override rate і частка звернень, закритих без людини |

**Чесно:** людині все одно лишається приблизно половина звернень (`zones.md` §0), а після розширення HUMAN-ONLY — більше, ніж до нього. Виграш не в кількості, а в тому, що кожне звернення приходить **повним**, апрувер відомий заздалегідь, а рішення має слід.

### Exceptions and Edge Cases

| Scenario | What to Do |
|---|---|
| Апрувер у відпустці (HRIS) | бот не обирає делегата → HUMAN; делегата призначає людина |
| Бот / LLM недоступні | fail-closed: усе → людина (ADR-0002); AUTO-дії людина виконує за runbooks вручну |
| Термінове «до 12» на HUMAN-ONLY | пріоритет P2, але перевірки ті самі. Терміновість + скидання / обхід HRIS — ознака соц. інженерії |
| IAM-інженер у відпустці | HUMAN-ONLY бере заступник із доступом до runbooks і handoff; бот працює далі (AUTO / DEFLECT / NEED_INFO) |
| Людина не згодна з маршрутом бота | override + причина в журналі → огляд щотижня → PR у policy |
| Security-подія вночі | пейдж on-call security, IAM — I |

### Metrics

| Metric | Target | How to Measure |
|---|---|---|
| Override rate | зниження з тижня на тиждень; AUTO — 0 overrides | журнал рішень vs фінальна дія людини |
| Частка закритих без людини (AUTO + DEFLECT) | baseline у shadow, далі зростання | розподіл маршрутів |
| Частка звернень, що дійшли до людини повними | > 90% | HUMAN без кола уточнень |
| Час до першої відповіді | бот — секунди; людина — у межах SLA пріоритету | мітки часу Slack |
| `kb_gap` на тиждень | зниження | беклог у Notion |
| Дії бота поза allowlist | **0** | алерт |
