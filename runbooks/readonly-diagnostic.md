## Runbook: read-only діагностика входу

**Owner:** IAM | **Frequency:** за запитом (AUTO) | **Last Updated:** 2026-10-07 | **Дія в policy:** `readonly_diagnostic`

### Purpose

Пояснити, **чому** людину не пускає: зняли доступ, блокує атака чи збій застосунку. Нічого не змінює. Діагностика виконується навіть тоді, коли маршрут далі піднімається (до APPROVAL чи SECURITY), бо вона лише читає.

### Prerequisites

- [ ] Автор = суб'єкт: дивимось лише **власний** журнал автора. Діагностику чужого доступу (#84) робить людина (`on_behalf` → HUMAN-ONLY).
- [ ] Застосунок працює через SSO (`sso: okta`). Для non-SSO System Log нічого не скаже → NEED_INFO: скрін і час.
- [ ] Бот має **read-only** scope на System Log. TODO(verify): мінімальний scope для `/api/v1/logs`.

### Procedure

#### Step 1: Події автора за 72 години
```
GET /api/v1/logs?filter=target.alternateId eq "<email>"&since=<now-72h>
```
**Expected result:** список подій (може бути порожній).

#### Step 2: Класифікувати знахідку

| Знахідка | Що далі | Приклад |
|---|---|---|
| `group.user_membership.remove` автоматичним правилом | доступ зняли легітимно (зміна відділу) → **APPROVAL** власника на повторну видачу | #69 Tableau |
| невдалі входи з чужих IP + `user.account.lock` | **SECURITY**, P1: можлива атака на акаунт | #42 «по вечорах» |
| подій немає | проблема, ймовірно, в застосунку → **NEED_INFO** (скрін, час) | #1, #3, #15 |
| знахідки неоднозначні | NEED_INFO, а **не** «усе ок» | — |

#### Step 3: Записати дію і відповісти
Журнал: `action = readonly_diagnostic`. Користувачу — нейтральне формулювання: не «підозра на атаку», а «бачу спроби входу не з твоїх пристроїв, передав у security, зміни пароль через self-service».

### Troubleshooting

| Symptom | Likely Cause | Fix |
|---|---|---|
| Подій немає, але людину не пускає | non-SSO застосунок або проблема на його боці | NEED_INFO; для non-SSO — людина дивиться в адмінці застосунку |
| Затримка подій | System Log не миттєвий | повторна діагностика за кілька хвилин, не одразу висновок |
